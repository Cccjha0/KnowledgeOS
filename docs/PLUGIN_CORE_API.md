# Plugin/Core Command API v1

Milestone F freezes a single integration boundary: the Obsidian plugin calls the Core Command API;
it never reads KnowledgeOS implementation files directly. The desktop transport in v1 is the local
CLI:

```text
node <core-cli-path> api <method> --vault <vault-path> --request-id <id> --input <json-object>
```

Every response is one JSON envelope. `api_version` is `"1"`; incompatible changes require a new API
version. `request_id` is generated by the caller and is the idempotency/correlation identity for a UI
action.

## Frozen methods

| Method | Input | Successful data | Delivery |
|---|---|---|---|
| `getTodayItems` | `refresh_markdown?: boolean` | `TodaySnapshot` | F02 |
| `createCapture` | `content`, optional `title`, `module_id`, `instance_id`, `content_type`, `attachments`, `active_path`; `preview_only` for context preview | capture path and routing summary | available |
| `listInboxItems` | optional `module_id`, `instance_id`, `state` | grouped Inbox items | F02 read model |
| `processInboxItem` | `item_id`, optional routing override and `preview_only` | run summary or waiting state | F04 contract; implementation pending |
| `processInboxBatch` | explicit `item_ids`, `mode: high-confidence`, optional module/instance filter | batch summary and per-item results | F04 contract; implementation pending |
| `listReviewItems` | optional `statuses`, module/instance/priority filters | Review Items with Vault-relative paths | available |
| `resolveReview` | `review_id`, `decision`, `user_comment?`, `modified_value?`, `review_after?` | persisted review execution result | available |
| `getModules` | none | module summaries and active-instance counts | available |
| `getInstances` | optional `module_id` | instance summaries | available |
| `getRecentRuns` | optional `limit` (1–100), `status` | recent run summaries | available |
| `getRunDetails` | `run_id` | run log, user summary and transaction record | available |
| `rollbackRun` | `run_id` | rollback status and plan identity | available |

An endpoint whose implementation belongs to a later F stage is callable and returns the stable
`CAPABILITY_NOT_READY` error. This currently applies to Inbox processing and prevents clients from
inventing temporary file-level fallbacks.

`createCapture` uses the caller's `request_id` as its idempotency identity. Retrying the same content
with the same ID returns the original result; reusing the ID with different content is rejected.
`preview_only: true` performs routing inference without writing a receipt, file, plan, log, or counter.

## Response and UI state

```json
{
  "api_version": "1",
  "request_id": "PLUGIN-...",
  "method": "getTodayItems",
  "state": "completed",
  "ok": true,
  "data": {},
  "error": null
}
```

The only UI states are:

```text
ready, loading, running, waiting-for-user, waiting-for-ai,
waiting-for-network, completed, failed, cancelled
```

The response state is authoritative. Closing a panel does not cancel Core work. Reopening the panel
must query Core again instead of reconstructing state from plugin memory.

## User-facing error model

Errors always contain:

```text
code
message
what_happened
impact
recovery_actions[]
retryable
technical_details
```

Normal UI shows the first five fields. `technical_details` is reserved for developer mode. A failed
response must never be displayed as success, and retry controls are shown only when `retryable` is true.

## Forbidden plugin access

The plugin must not directly:

- read or write Review Queue, State, Logs, Cache, module manifests, instance YAML, or business files;
- parse frontmatter or validate Schema;
- choose a module, target path, risk level, or final Today rank;
- execute Operation Plans, Git commands, migrations, prompts, or rollback files;
- maintain a private copy of Today, Inbox, Review, Run, module, or instance state.

Opening a Vault-relative target returned by Core in Obsidian is permitted. Storing UI preferences and
Core/Vault connection paths in plugin settings is also permitted.
